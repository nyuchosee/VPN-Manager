# VPN Manager

> **Telegram-бот для управления VPN-подписками через API 3x-ui.** Заявки и продления, сроки и лимиты, HWID-устройства, тикеты поддержки, уведомления об окончании подписки и административное меню, временные блокировки Telegram ID (всего бота или только поддержки). Работает через Telegram long polling: отдельный веб-сервер и входящий порт для бота не нужны. По умолчанию изменение клиентов отключено.

## 1. Системные требования

- Linux с `systemd`, правами `sudo` и доступом к интернету; ориентир — Ubuntu/Debian с Python **3.10+** и модулем `venv`.
- Установленный `git` для получения проекта из GitHub (на Ubuntu/Debian при необходимости: `sudo apt-get update && sudo apt-get install -y git`).
- Действующая панель **3x-ui** с HTTPS-доступом к API и заранее созданными Inbound (совместимость конкретной версии следует проверять диагностикой).
- Отдельный Telegram-бот и его токен от BotFather, числовой Telegram ID администратора, API Token панели, HTTPS-адрес панели и шаблон URL подписки.
- `python3`, `tar`, `systemctl`; зависимости Python устанавливаются мастером. `nginx` и Xray не переустанавливаются.
- Перед установкой/обновлением — резервная копия панели и доступ к аварийной консоли VPS.

## 2. Установка и команды

**Шаг 1. Клонируйте репозиторий на сервер.** Замените `OWNER/REPOSITORY` именем владельца и названием своего публичного репозитория на GitHub (ветка `main`):

```bash
git clone --depth 1 --branch main https://github.com/OWNER/REPOSITORY.git vpn-manager
cd vpn-manager
```

**Шаг 2. Проверьте целостность установщика** (команды выполняются из каталога `vpn-manager`):

```bash
(cd dist && sha256sum -c SHA256SUMS)
bash dist/vpn-manager-setup-0.5.6.sh --verify
```

**Шаг 3. Запустите мастер установки** (или безопасного обновления, если бот уже установлен):

```bash
sudo bash dist/vpn-manager-setup-0.5.6.sh
```

Мастер последовательно запросит токен Telegram, ID администратора, HTTPS URL и API Token 3x-ui, список ID существующих Inbound и шаблон подписки. Ввод секретов скрыт. При первоначальной установке выполняется резервирование панели и проверка API **без записи**. При обновлении прежняя SQLite и конфигурация сохраняются; требуется заранее выключить режим записи.

**Если репозиторий уже клонирован и вышло обновление:** сначала сделайте резервную копию и отключите запись, затем получите изменения из `main`, проверьте новый установщик и запустите его. Пример для версии 0.5.6:

```bash
sudo vpn-manager-write-mode --disable
sudo vpn-manager-backup --all
cd vpn-manager                 # если вы находитесь в каталоге, содержащем vpn-manager
git pull --ff-only origin main
(cd dist && sha256sum -c SHA256SUMS)
bash dist/vpn-manager-setup-0.5.6.sh --verify
sudo bash dist/vpn-manager-setup-0.5.6.sh
```

**После установки:**

```bash
sudo systemctl status vpn-bot --no-pager
sudo vpn-manager-probe
sudo vpn-manager-doctor --api
sudo journalctl -u vpn-bot -n 50 --no-pager
```

**Управление:**

```bash
sudo vpn-manager-configure           # изменить настройки; запись будет отключена
sudo vpn-manager-inbounds            # изменить Inbound для новых пользователей
sudo vpn-manager-backup --all        # резервная копия приложения и панели
sudo vpn-manager-backup --bot        # только локальные данные бота
sudo vpn-manager-write-mode         # выбрать чтение / запись
sudo vpn-manager-write-mode --disable
sudo systemctl restart vpn-bot       # перезапуск бота
sudo vpn-manager-uninstall           # удаление бота с подтверждением
```

После настройки сначала проверьте работу `/start`, `/admin` и диагностических команд на тестовом клиенте. Операции записи разрешайте только после проверки совместимости. Справочные инструкции: [установка](docs/INSTALLATION_RU.md), [администрирование](docs/OPERATIONS_RU.md), [резервные копии](docs/BACKUPS_RU.md), [безопасность](docs/SECURITY_RU.md), [публикация на GitHub](docs/PUBLISHING_RU.md).

### XTLS Vision для базового REALITY inbound #1 (v0.5.4)

Если в `INBOUND_IDS` выбран **только `1`**, бот перед выдачей нового доступа проверит, что inbound #1 включён и использует VLESS + TCP/RAW + REALITY, и создаст клиента с `flow=xtls-rprx-vision`. При несовпадении параметров операция будет остановлена до изменения в панели. Для других вариантов списка inbound поведение v0.5.2 сохранено — поток Vision не назначается автоматически. В панели возможна иная нумерация; проверьте конфигурацию до выбора ID 1.

**Существующих клиентов обновляйте отдельно** после бэкапа через `scripts/migrate_reality_vision.py`: сначала только предварительный просмотр, затем тест на одном клиенте и только потом общая миграция. Инструкция: [миграция REALITY и Vision](docs/VISION_MIGRATION_RU.md). После изменения `flow` обновите подписку в клиентских приложениях, иначе соединения могут перестать работать.

### Напоминания об окончании подписки (v0.5.4)

Бот **автоматически уведомляет** пользователей с привязанной действующей подпиской **за два и за один календарный день до окончания срока** (по UTC). Время начала отправки — **09:00 UTC / 12:00 МСК**; служба проверяет сроки раз в 15 минут и отправляет не более одного уведомления в календарные сутки на пользователя. Если бот перезапущен после указанного часа, проверка происходит после запуска. Пропущенные целые дни не компенсируются задним числом. Уведомления о сроках **не меняют ничего в 3x-ui** и работают даже при `WRITE_ENABLED=false`.

Сообщение начинается с `❗❗❗ ВНИМАНИЕ! ❗❗❗` и содержит кнопку **«✅ Ознакомился»**. При нажатии бот удаляет именно это уведомление; если Telegram уже запрещает удаление старого сообщения (обычно после 48 часов), бот заменяет его текст короткой отметкой без кнопки. Подтверждение первого дня не отменяет напоминание следующего дня. При продлении бот учитывает новую дату окончания из панели.

Настройки необязательны в `/etc/vpn-bot/bot.env` (для действующей установки значения применяются по умолчанию):

```ini
EXPIRY_REMINDERS_ENABLED=true
EXPIRY_REMINDER_HOUR_UTC=9
```

После изменения файла перезапустите `sudo systemctl restart vpn-bot`. Расширенные правила, ограничения Telegram и диагностика: [инструкция по напоминаниям](docs/EXPIRY_REMINDERS_RU.md).

### Проверка уведомлений на реальных пользователях (v0.5.6)

Администратор может вызвать `/testreminder TG_ID 2` или `/testreminder TG_ID 1`, чтобы отправить **тестовое** предупреждение одному привязанному пользователю. Команда запускает общий механизм напоминаний с виртуальным сроком и реальной кнопкой «Ознакомился», не меняет 3x-ui и не занимает ежедневную квоту настоящих уведомлений. Дата в тестовом сообщении условная и прямо так обозначена. Подробности — `docs/EXPIRY_REMINDERS_RU.md`.

### Временные блокировки Telegram (v0.5.5)

Администратор может **отдельно** запретить пользователю доступ ко всему боту или только к тикетам поддержки. Запрет поддержки исключает и ответы в ранее открытом тикете; заявки и остальные функции продолжают работать. **VPN-доступ в панели 3x-ui при этом не блокируется.** Оба ограничения привязаны к Telegram ID, действуют указанное администратором количество полных суток и снимаются автоматически после истечения срока. Досрочно их можно снять вручную; все действия журналируются в SQLite.

Откройте `/admin` → «🚫 Ограничения» → карточку пользователя. В ней можно нажать «Запретить бот» / «Запретить поддержку», **ввести срок в днях**, или снять соответствующее ограничение. Карточка доступна также через `/moderation TG_ID` или из `/client TG_ID`. Для прямого управления:

```text
/banbot TG_ID DAYS        # запрет всего бота
/bansupport TG_ID DAYS    # запрет обращений в поддержку
/unbanbot TG_ID           # снять полный запрет
/unbansupport TG_ID       # снять запрет поддержки
/bans                     # действующие блокировки
```

Функция активна сразу после обновления, **не требует** `WRITE_ENABLED=true`, дополнительного расписания или изменений в панели. Дополнительные сведения: [ограничения Telegram](docs/TELEGRAM_BANS_RU.md).

## 3. Возможные ошибки и решения

| Ошибка или симптом | Что проверить |
|---|---|
| `203/EXEC` / `Permission denied` | Права на `/opt/vpn-bot/.venv`, запуск Python от системного пользователя `vpn-bot`: `sudo vpn-manager-doctor`. |
| Бот не отвечает на `/start` | `systemctl status vpn-bot`, журнал `journalctl -u vpn-bot`, корректность Telegram-токена, конфликт `409 Conflict` с другим процессом polling. |
| API недоступен / `401` / `403` | HTTPS URL панели, секретный base path, срок действия API Token; выполнить `sudo vpn-manager-probe`. |
| `PANEL_REJECTED` / неверный формат JSON | Совместимость полей API 3x-ui; **не повторять** спорную операцию до сверки фактического клиента в панели. |
| Inbound отсутствует или выключен | Найти ID и состояние в 3x-ui; выполнить `sudo vpn-manager-inbounds`. |
| Операция `needs_review` | Сверить состояние клиента через панель и `/ops`; не подтверждать повторно автоматически. |
| Неверная ссылка подписки | Исправить шаблон с единственным `{sub_id}` через `sudo vpn-manager-configure`. |
| Ошибка обновления | Проверить резервную копию, статус службы и `sudo vpn-manager-doctor --api`; не удалять SQLite ради переустановки. |

> Программное обеспечение предназначено для самостоятельного администрирования. Локальные тесты не гарантируют совместимость каждого API или безопасность развёрнутой инфраструктуры. Не публикуйте токены, базы, резервные копии и действующие ссылки подписок.
